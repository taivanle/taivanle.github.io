AGENT CONTROLS · VERIFICATION

Did the agent do only what was approved?

A TypeScript verifier that checks approval boundaries against actual state changes and keeps missing evidence visible.

The challenge

An allowed decision does not prove that an action was correct. Approval can refer to the wrong target, cross an account boundary, or become unverifiable when post-execution evidence is unavailable.

Conceptual flow · simplified to explain the engineering approach.

THE DESIGN DECISION

Verify the observable effect, not just the control's returned decision. Missing state evidence remains inconclusive, so a successful function return cannot silently become a security pass.

What I built

  1. Built a dependency-free TypeScript demonstration around a synthetic ticket store, with deliberately broken and corrected reference controls.
  2. Ran five isolated scenarios covering an approved action, missing approval, a changed ticket target, customer separation, and unavailable post-execution evidence.
  3. Compared before-and-after state with the authorised action and produced a self-contained HTML and JSON report with explicit pass, fail, and inconclusive results.

Scope & reflection

This verifies our own synthetic reference example. It is a local demonstration, not a production security product or a customer vulnerability finding. Real identity, transport, concurrency, expiry, and customer-system adapters require separate work.

What I take forward

A useful verifier must be willing to say it cannot conclude. Keeping uncertainty visible is as important as detecting a seeded failure.
